# END-Samurai 企画書 ― α版実装仕様書

本書は、企画書（01〜07）を**実装に着手できる状態**へ落とすための仕様書である。設計の「何を作るか」は01〜07が持ち、本書は「**どう作るか／α版で何を切り出すか**」を定める。

> **数値モデルの非重複方針：** 戦闘の計算式・基準値・状態異常X値などの**数値モデルは01「戦闘の数値モデル」「状態異常」／02「気力防御パラメータと回復・貫通の数値モデル」に一元化されている**。本書はそれらを**参照**するに留め、再記述しない（企画書の一元化方針に準拠）。本書が新たに定義するのは、アーキテクチャ・データスキーマ・状態モデル・画面フロー・α版コンテンツの切り出し・実装フェーズである。

## 1. アーキテクチャ方針

### 1.1 レイヤー分離（最重要原則）

Godot移植を見据え、**ゲームロジックをエンジン非依存の純粋TypeScriptコアに完全分離**する。

```
┌─────────────────────────────────────────────┐
│  UI 層 (ui/)         描画・入力・アニメーション     │  ← 差し替え対象（Godotで書き直す）
│   └ core を呼ぶだけ。状態は持たない              │
├─────────────────────────────────────────────┤
│  App 層 (app/)       画面遷移ステートマシン        │  ← 薄い。Godotではシーン遷移に対応
├─────────────────────────────────────────────┤
│  Core 層 (core/)     ★エンジン非依存・純粋関数★     │  ← Godotへ「実行可能な仕様」として移植
│   ├ model   型定義（状態・データ）                │
│   ├ rules   戦闘解決・計算式・我慢/絶頂/射精・とどめ  │
│   ├ content データローダ（JSON→型）              │
│   └ rng     シード付き決定論的乱数                 │
├─────────────────────────────────────────────┤
│  Data (data/)        JSON コンテンツ              │  ← ★そのままGodotへ持ち込む★
└─────────────────────────────────────────────┘
```

**Core層の鉄則：**
- DOM / Phaser / Godot / `window` / `fetch` 等を**一切importしない**。
- **副作用を持たない**。状態遷移は「現在の状態を受け取り、新しい状態＋発生イベント配列を返す」純粋関数で表現する。
- **乱数は外部から注入**（`rng` を引数で渡す）。グローバル `Math.random()` を直接呼ばない。これにより決定論的リプレイ・テスト・Godot移植時の挙動照合が可能になる。
- I/O・時間・アニメーションを知らない。「いつ・どう描くか」はUI層の責務。

この分離により、Godot移植時は**Core層のロジックをGDScript/C#へ読み替えるだけ**で済み、UI層のみ作り直す。Core層は「実行できる仕様書」として機能する。

### 1.2 イベント駆動の状態遷移

戦闘解決は次の形に統一する：

```ts
// 純粋関数。state は不変（新しい state を返す）
function resolveCardPlay(
  state: BattleState,
  cardId: string,
  targetId: string | null,
  rng: Rng
): { state: BattleState; events: BattleEvent[] }
```

`BattleEvent`（例：`DamageDealt`, `BlockGained`, `PartDegraded`, `StatusApplied`, `ComboTriggered`, `EnemyDefeated`, `KoyukiReaction`）を返し、**UI層がイベント列を順に再生して演出する**。ロジックは「何が起きたか」だけを返し、「どう見せるか」は持たない。Godot移植時も同じイベント列をGodotのアニメーションへ流せる。

### 1.3 ディレクトリ構成（案）

```
/src
  /core
    /model      run-state.ts, battle-state.ts, card.ts, enemy.ts, sword.ts, status.ts, companion.ts, sextech.ts
    /rules      normal-battle.ts, charm-battle.ts, damage.ts, status.ts, sword-degrade.ts, development.ts, combo.ts
    /content    loader.ts, schema.ts (zod等で実行時バリデーション)
    /rng        rng.ts (mulberry32等のシード乱数)
  /data
    cards.json, enemies.json, companions.json, sextech-cards.json,
    map-inaka.json, events.json, text.json, blessings.json (αは空でも可)
  /ui
    /screens    title, prologue, map, battle, charm-battle, reward, camp, event, gameover, result
    /components card-view, enemy-view, sword-status, ap-bar, hand, intent-badge, status-icon
  /app          game.ts (画面遷移ステートマシン), main.ts (エントリ)
/test           core/ のユニットテスト（純粋関数なのでテスト容易）
```

### 1.4 推奨ライブラリ（軽量・移植の足枷にしない）

- **言語：** TypeScript（strict）。
- **描画：** まずは**プレーンなDOM＋CSS**（カードゲームのUIはDOMで十分かつ移植時に捨てやすい）。アニメーションが要れば後から軽量canvasを部分導入。Phaserは採用しない（Core分離方針と二重管理を避ける）。
- **データ検証：** zod等でJSONを実行時バリデーション（スキーマずれを早期検出）。
- **乱数：** 自前のシード乱数（mulberry32）。Core層に同梱。
- **バンドラ：** Vite（開発サーバ＋ビルド）。
- **テスト：** Vitest（Core層の純粋関数を重点的に）。

> UIをDOMにする理由：α版は「使い捨て・ロジック検証用」であり、リッチな演出より**ロジックの正しさとループの面白さの検証**が目的。DOMは実装が速く、捨てやすく、Core分離を最も自然に保てる。

## 2. データスキーマ（JSON）

全コンテンツをエンジン中立なJSONに外部化する。**これがGodotへそのまま持ち込める最重要資産**。以下はα版に必要な最小スキーマ（TypeScript型として記述。実体はJSON）。

### 2.1 カード（技・道具）

```ts
type CardCategory = "skill" | "item" | "companion_active";
type TargetType = "single" | "all" | "pierce" | "self" | "self_aoe";
type SwordPart = "blade" | "tsuba" | "tsuka"; // 刀身・鍔・柄

interface CardDef {
  id: string;
  name: string;            // 表示名（"斬る" 等）。text.json で多言語化も可
  category: CardCategory;
  ap: number;              // 基本AP消費（刀段階補正は実行時に適用）
  target: TargetType;
  flavorKey?: string;      // フレーバーテキストの参照キー（text.json）
  // 効果は宣言的に列挙（rules が解釈）
  effects: CardEffect[];
  // 使用条件（刀段階・前ターン未行動 等）
  requirements?: CardRequirement[];
  // 道具カード用
  uses?: number;           // 残り回数（item のみ）
}

type CardEffect =
  | { kind: "attack"; multiplier: number; ignoreDefense?: boolean }   // 刀身攻撃力×倍率
  | { kind: "fixed_damage"; amount: number; ignoreDefense?: boolean } // 柄打ち等
  | { kind: "block"; amount: number }                                  // 受ける等
  | { kind: "dodge_next" }                                             // 見切る
  | { kind: "enemy_defense_down"; amount: number; duration: "battle" | number } // 崩し打ち
  | { kind: "apply_status"; status: StatusId; x: number; toTarget: boolean }
  | { kind: "repair_part"; part: SwordPart; toStageMax?: string }      // 修繕。回復上限段階
  | { kind: "heal"; amount: number }                                   // きずぐすり
  | { kind: "cure_status"; count: number }                             // まじない札
  | { kind: "self_degrade"; part: SwordPart; stages: number };         // 自傷コスト

type CardRequirement =
  | { kind: "blade_stage_at_least"; stage: string }   // 刀身「切れ味低下」以上 等
  | { kind: "no_action_last_turn" };                  // 居合
```

段階の補正値（攻撃力・AP・防御・連撃率・デバフ無効化率）は**01「刀の状態段階と補正値」を単一情報源とし、JSONへ転記する**（ハードコードしない）。

```ts
interface SwordPartStages {

    name: string;          // "なまくら" 等

    mods: {
      attack?: number; ap?: number; baseDefense?: number;
      comboRate?: number; debuffNullifyRate?: number;
    };
  }[];
  baseStageId: string;     // 基準＝"新品同様"
}
```

01「敵行動アーキタイプ」の6型を `archetype` として持ち、行動はデータ駆動の予告テーブルで表現する。

### 3.1 RunState（1ラン全体・セーブなしなのでメモリ常駐）

## 4. 通常戦闘（HP戦）の実装

ターン構造（①開始→②行動→③敵行動→④終了）は**01「ターン構造」をそのまま実装**。計算式・基準値・部位デバフ確率・連撃・崩し・「受ける／いなす」は**01「戦闘の数値モデル」を単一情報源として参照**。

実装上の要点（本書が補う点）：

- **加算プール→倍率の順序**を `rules/damage.ts` の単一関数に閉じ込める（01の式 `max(1,(基礎+段階+プール)×倍率−敵防御)` を1関数で）。二重掛けを構造的に不可能にする。
- **防御無視フラグ**（連撃・柄打ち）は `CardEffect.ignoreDefense` で宣言的に表現し、`damage.ts` が分岐。
- **連撃**は攻撃解決後に `combo.ts` が `comboRate` で抽選し、即時に追加 `DamageDealt` イベントを積む（プレイヤーは結果を見て次手を選べる＝01準拠）。
- **「受ける／いなす」**は狙撃型の部位狙い予告ターンのみ、敵行動フェイズ直前にワンタップ選択を挿入（既定＝受ける）。`いなす` は被ダメ+50%・部位確定防御（01準拠）。
- **隠匿型「？？？」**は `concealEffect:true` の予告を「数値表示・効果種別アイコンを?」でUI表示し、防御値で受け切れば随伴無効（01のフェアネス保証）。

## 5. 魅了バトル（最小実装）

02「魅了バトル」を**最小スコープで**実装。α確定：**性技系専用**（仲間アクティブ・通常技は持ち込み不可）／置き場は**プロローグお豊＋道中むすめしかばね**。

実装する機能（02「我慢ゲージと絶頂・射精」の再設計を反映）：
- **二層ゲージ：** 敵＝気力＋我慢／こゆき＝HP＋我慢（HPバーは魅了では出さず、気力・我慢ゲージを左右対称表示）。こゆきHP0で敗北。
- **性技カード8種＋狙い撃ち射精技2種＋とどめ！**（2.6）。属性は裏管理・非表示。
- **我慢ゲージ機構：** 性技は敵の気力＋我慢を削る。敵の我慢0→**絶頂**（気力大ダメージ＋直近属性が1段弱化＋我慢再充填）。四十八手はこゆきの我慢を削り、0→**射精**（暴発＝HP大減・不利／狙い撃ち＝敵を崩す）。我慢は毎ターン少量自然回復＋乳繰りで能動回復。
- **部位弱化（旧開発の置換）：** 絶頂・狙い撃ち射精で、突かれた属性の弱点段階が1上がる。`development` カウント方式は廃止。
- **与気力ダメージ式／与我慢式：** 02「気力防御パラメータと回復・貫通の数値モデル」を参照（加算→弱点倍率→気力防御減算、裏取りは×2参照／与我慢＝与気力+1）。
- **「とどめ！」**：常時手札・デッキ非投入。**敵の気力0（放心）でのみ使用可・ノーコスト確殺**（02準拠。割合コスト版・突いた回数は廃止）。撃破で救済者カウント+1（お豊は加入）。
- **せっくすてくの軸：** 威力＝身＋鎬／守り＝鎬＋切先（我慢被ダメ軽減）／我慢タフネス＝身＋切先（gamanMax＋・射精威力＋）。3ターンごとにポイント獲得→割り振り（自動割り振りボタンも実装）。

α版で**実装しない**（明示的に除外）：
- 複数魅了戦・合体攻撃・「みんなでとどめ！」（むすめしかばねは単体遭遇に限定）。
- しらせ戦・四十八手のしらせ専用技・複合/複数性技カード。
- 敵リアクション（弱点突かれリアクションはお豊くちづけのみ最小実装。他はフックのみ）。
- 弱化の個体永続スコープ（αは遭遇内リセットのみ＝通常敵スコープで足りる）。

> プロローグのお豊戦は「操作チュートリアル」、道中むすめしかばねは「斬る！／とろかす…♡の二択＋救済」の検証。両者で別々の検証目的を満たす（決定どおり）。

## 12. Godot移植時の引き継ぎ方針

α版（ブラウザ）からGodotへ移すとき、何を捨て・何を運ぶかを明示する。

| 資産 | 引き継ぎ | 方法 |
|---|---|---|
| **Data（JSON）** | ◎ そのまま | Godotの `JSON.parse` / Resource へ流し込む。**最重要資産** |
| **Core層ロジック** | ○ 読み替え | 純粋関数・決定論なので、GDScript/C#へ1対1で移植。**実行可能な仕様**として機能。シード乱数の挙動も照合可能 |
| **イベント列（BattleEvent）の設計** | ○ 流用 | UI演出の駆動方式をGodotのアニメーションへ移植 |
| **UI層（DOM）** | ✕ 破棄 | Godotのシーン/Controlで作り直し |
| **テキスト（text.json）** | ◎ そのまま | Godotのローカライズ/データへ |

**移植を楽にするため、α版実装中も死守する規律：**
1. Core層にエンジン依存を混入させない（DOM/`window`禁止）。
2. 乱数は必ず注入。グローバル乱数を呼ばない。
3. 数値・テキスト・コンテンツは必ずJSONへ。コードにハードコードしない。
4. 計算式は01/02の単一情報源に対応する関数に閉じ込め、二重実装しない。
